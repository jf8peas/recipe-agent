The core idea

Every stage is saved — so you can rewind, edit, and replay

Nothing the agent produces is ever overwritten. Each stage's result is kept as its own checkpoint, and each checkpoint remembers the one before it. That means you can go back to any earlier point in a run, change something, and continue from there — without disturbing the original.

Architecture

Six steps, browser to graph and back

1 · BROWSER

Type

onChange → setRaw(value)

Every keystroke updates the raw string via React state. Nothing else happens yet.

2 · BROWSER

Clean up

split → trim → filter

Plain JS, not Zod. raw is consumed here — ingredients is what moves on.

3 · BROWSER → NETWORK

fetch()

POST /api/…/start

The one real network hop — a genuine HTTP POST leaves the browser.

4 · SERVER

Validate

RequestSchema.safeParse(…)

✓ the actual gate — Zod's first check. Fails → 400, stops here.

5 · SERVER

Invoke

graph.invoke(seed, config)

Same process, no network. Runs exactly one node — interruptAfter is set on all seven.

6 · SERVER → NETWORK

Respond

NextResponse.json({ state, next })

Travels back over the same fetch() call — its promise resolves with this.

Loops back to the browser, always — never a server-side loop. Step waits for a click; Auto-run is the browser's own loop firing the next fetch() immediately, one full trip per node.

Only two hops ever leave a process: step 3 (browser → server) and step 6 (server → browser). Everything else — the clean-up in step 2, the validation in step 4, the graph call in step 5 — runs as a plain function call, no network involved. The node that step 5 runs makes its own call to OpenRouter, Zod-checked the same way as step 4 — see the next section for model routing.

Every reply is requested through withStructuredOutput against a Zod schema — a model's answer is validated shape before anything trusts it. MODEL_DEFAULT and MODEL_CRITIQUE are OpenRouter model IDs read only in lib/agent/models.ts — swapping models is an env-var change, never a code change.

State, validation & persistence

One state object, replaced whole, checkpointed in Postgres

One shared state object — not per-node variables — flows node to node. Its shape is GraphState (Annotation.Root in lib/agent/graph.ts): one last-value-wins channel per field, replaced whole on every update, never merged.

Zod (StateSchema, lib/agent/state.ts) isn't an automatic guard on every transition. It validates exactly two moments a node's own code checks: a model's structured output the instant it returns, and a person's /fork edit patch — before either is trusted to overwrite a channel.

Branching mechanics

A fork never edits history — it replays a new one

Forking never writes a second, divergent continuation onto an already-used step in the same thread — that's the operation confirmed to lose data. Instead, lib/fork-replay.ts does this, in order:

1

Read the source branch's full checkpoint history, oldest first, up to the checkpoint being forked from.

2

Seed a brand-new LangGraph thread, and replay every prior stage's recorded output onto it, exactly as it happened.

3

Apply the user's patch as the final replayed step — attributed to the stage that originally produced it.

4

Record the new thread as a branch of the old one in a small branches table, and return its fresh tip.

One thread per branch

Every branch — the original run and every fork of it — is its own LangGraph thread_id. A session can hold many.

Fork vs. retry

A retry is a plain re-run on the same thread — confirmed safe. Only editing-and-continuing seeds a new one.

Data model

Three small tables that track sessions, branch lineage, and usage limits

sessions

  • session_id, client_id
  • root_thread_id, title
  • stage_count, status

One row per app-level session — not a LangGraph thread.

branches

  • thread_id, session_id
  • parent_thread_id
  • forked_from_checkpoint_id

One row per branch — links it to its parent and fork point.

usage_events

  • client_id, thread_id
  • kind, created_at
  • start | stage | rejected-limit

Backs the rate limits and daily/global caps.

How the browsable tree gets rebuilt

Neither piece alone is the tree. Each branch's own checkpoint chain (from LangGraph's checkpointer) gives a plain, unbroken line from its start to wherever it ends; the branches table records which branch forked from which checkpoint of which other branch. Combining the two produces the full, browsable history a person sees in the app.

API contract & guardrails

No login — just an anonymous ID and honest limits

Every request carries X-Client-Id

A random id in localStorage is the only credential. Missing it → 401. A session id belonging to someone else's client → 404, never 403 — ownership never leaks which sessions exist.

A stage failure isn't an HTTP error

A failed stage comes back as 200 with a stage-failure entry in the timeline, so the client can render it in the tree and offer a retry.

Four kinds of limit, one status code

rate-limited, daily-cap, global-cap, session-cap — each returns 429, and no checkpoint is ever written for a rejected request.

Engineering principles

Six non-negotiables from the project's own constitution

Stack is fixed

Next.js on Vercel, LangGraph.js in Route Handlers, OpenRouter for every model call, Neon + Zod.

Singletons, always

One pool, one compiled graph, cached in module scope — never created inside a request handler.

One thread per branch

Never a second child of an already-branched checkpoint in one thread — the confirmed data-loss case.

Model IDs, one place

Only lib/agent/models.ts resolves a model id. Design tokens live only in app/tokens.css.

One super-step per request

interruptAfter on every node; Auto-run is a client-side loop of single-step requests, not a server loop.

Device-private, always

No login, no session id in a URL, no sharing across devices — by design, not by omission.
